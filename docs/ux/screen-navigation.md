# 화면 전환·조작 문법 기획 — 탭 우선(tap-first) 전환 (초안)

> 문서 상태: 초안 (팀 리뷰 전)
> 선행 문서: docs/screen-design.md, docs/ux/accessibility-guidelines.md, docs/ux/design-principles.md, docs/ux/feedback-mapping.md, docs/research/blind-camera-ux-notes.md
> 코드 기준: `MainActivity.kt`(AppScreen 상태 배선·볼륨 핸들러), `HomeScreen.kt`, `GalleryScreen.kt`, `SettingsScreen.kt`, `ResultScreen.kt`, `CaptureScreen.kt`

## 목적

조작의 중심을 **볼륨 버튼에서 화면 탭으로 옮긴다.** 볼륨 버튼은 전환기 동안만 병행 유지하고,
탭 문법이 검증되면 제거한다(팀 방침). 동시에 화면 사이의 이동(전환·복귀)에
"어디서든 같은 문법"을 세운다.

### 왜 볼륨 버튼을 내리는가

- **셔터 순간에 기기를 눌러 흔든다.** 조준이 완성된 바로 그 순간 옆면을 쥐어짜는 동작은
  편차를 다시 벌린다. 탭도 기기를 건드리지만 쥐는 힘의 변화가 훨씬 작다. [추정 — 편차 로그로 검증 가능]
- **위치 탐색 비용.** 기기·케이스마다 버튼 위치와 조작감이 다르고, 파지를 바꿔 손가락을
  옮겨 짚어야 한다. 반면 "화면 아무 곳"은 찾을 필요 자체가 없다.
- **짧게/길게 오버로딩.** 같은 버튼이 상태에 따라 4가지 의미를 갖고, 짧게 누르려다 1초를
  넘기면 세션이 통째로 취소된다 — 실수 비용이 크다.
- **주 사용자가 잔존시력이 있다.** 물리 버튼의 유일한 강점은 "안 보고도 찾을 수 있다"인데,
  화면 전체를 타깃으로 쓰면 탭도 같은 강점을 갖는다. 전맹 사용자에게도 TalkBack의
  "두 번 탭 = 실행" 관례와 일치해 오히려 익숙하다.
- **선행연구도 터치가 주류다.** 검토한 선행 시스템(②·④·⑤)은 모두 터치 기반이며,
  볼륨 버튼을 주 조작으로 쓴 사례가 없다. [근거 있음 — blind-camera-ux-notes]

단, 제거는 **탭 문법의 오조작률·성공률을 실사용자로 검증한 뒤**에 한다.
물리 버튼을 선호하는 사용자가 있을 수 있어(연구① "선호 다양성"), 검증 전까지는
기존 볼륨 매핑을 건드리지 않고 병행한다.

## 1. 현재 화면·전환 지도 (코드 기준 as-is)

### 화면과 기능

| 화면 | 구현 | 할 수 있는 것 |
|---|---|---|
| S1 온보딩 | `OnboardingScreen` (최초 1회) | 앱 소개·권한 요청 → "계속" 버튼으로 홈 |
| S2 홈 | `HomeScreen` — 카메라 위 오버레이 | 세션 시작(마이크 원 터치 / 볼륨 짧게), 사진 찾기(하단 전폭), 설정(**우상단 작은 칩**) |
| S3 촬영 세션 | `CaptureScreen` + `CaptureSessionManager` | LISTENING/PARSING 동안은 홈이 계속 떠 있고, AIMING부터 조준 UI. 셔터=**볼륨 짧게뿐(터치 셔터 없음)**, 취소=볼륨 길게/"촬영 취소" 터치 |
| S4 결과 | `ResultScreen` — 오버레이, 저장 후 **자동 진입** | 요약·설명 낭독, 다시 듣기, 라벨 붙이기, "저장"→홈, "다시 촬영"→세션 |
| 사진 찾기 | `GalleryScreen` | 음성 검색, 결과 듣기, 사진 터치=설명 낭독, 복귀=**좌상단 ‹ 아이콘** |
| S5 설정 | `SettingsScreen` | 슬라이더 3종, 서버 주소, 얼굴 등록(→카메라 화면으로 점프), 복귀="돌아가기" TextButton |

### 전환 트리거와 확인 신호

| 전환 | 트리거 | 전환 시 청각·촉각 신호 |
|---|---|---|
| 홈 → 세션 | 볼륨 짧게 / 마이크 터치 | TTS "무엇을 찍을지 말씀해 주세요" ✅ |
| 세션 → 결과 | 자동 (저장 완료) | TTS "촬영했습니다" ✅ |
| 결과 → 홈 | "저장" 터치 | **없음** |
| 홈 → 설정 | 우상단 칩 터치 | **없음** |
| 홈 → 사진 찾기 | 하단 버튼 터치 | **없음** |
| 설정/사진 찾기 → 홈 | 화면마다 다른 터치 버튼 | **없음** |

`announceForAccessibility`/전환 안내 TTS 호출은 코드에 **한 건도 없다** —
screen-design.md 4절의 "상태 전환 시 즉시 낭독" 원칙이 세션 상태에만 구현되고
화면 전환에는 구현되지 않았다.

## 2. 문제 정의

1. **촬영의 유일한 트리거가 볼륨 버튼이다.** `CaptureScreen`에 터치 셔터가 없다.
   가장 중요한 동작이 가장 불편한 입력에만 걸려 있다.
2. **시스템 뒤로가기 = 앱 종료.** `BackHandler`/`onBackPressed` 처리가 없어서
   설정·사진 찾기·결과 화면에서 뒤로 제스처를 하면 홈이 아니라 앱 종료다.
   시각장애 사용자에게 뒤로가기는 위치를 찾을 필요 없는 유일한 전역 제스처라 가장 먼저
   시도하는 복귀 수단인데 결과가 최악이고, 설정의 서버 주소 적용도 건너뛴다.
3. **전환 확인 신호 부재.** 설정·사진 찾기에 드나들 때 아무 소리·진동이 없어,
   터치가 먹었는지·지금 어느 화면인지를 화면을 자세히 읽어야만 안다.
4. **복귀 문법이 화면마다 다르다.** 설정=하단 TextButton, 사진 찾기=좌상단 ‹ 아이콘,
   결과=하단 "저장", 세션=볼륨 길게. 4화면 4문법.
5. **결과 화면의 출구 안내가 없다.** 자동으로 나타난 화면인데 나가는 방법을 말해주지 않는다.
   볼륨 짧게=새 세션이라는 숨은 경로도 안내되지 않는다.
6. **모서리의 작은 타깃.** 설정 진입(우상단 칩)·사진 찾기 복귀(좌상단 ‹)는
   "모서리+소형+저대비" 조합으로 저시력에게 최악이고 48dp에도 미달한다.

## 3. 설계 원칙

1. **탭이 기본, 화면 전체가 타깃.** 진행 동작은 화면 어디를 두 번 탭해도 되게 한다.
   작은 버튼을 찾는 정밀 타겟팅을 없애는 것이 전맹·저시력 공통의 이득이다.
2. **문법은 두 개만.** "**두 번 탭 = 진행**(그 화면의 주 동작), **길게 누르기·뒤로가기 = 복귀**(홈)".
   화면이 바뀌어도 이 두 규칙은 바뀌지 않는다. [근거 있음 — 연구① "상호작용 횟수 적게",
   "초기에 한 번 설명"; TalkBack 두 번 탭 관례와 일치]
3. **허브&스포크 유지, 깊이 1 고정.** 홈이 유일한 허브. 새 화면·중간 단계를 추가하지 않는다.
4. **모든 화면 전환은 3채널로 확인시킨다.** earcon+햅틱 / TTS 1회("○○ 화면입니다") /
   대형 시각 헤더. TTS 1회 정책(feedback-mapping)을 그대로 따른다.
5. **같은 역할은 항상 같은 자리.** 상단=화면 정체, 하단=주 동작, 최하단=복귀.
   온스크린 버튼은 유지한다 — 제스처를 모르거나 못 쓰는 상황의 대체 경로다.
   [근거 있음 — WCAG 2.5.7 취지, accessibility-guidelines "터치 컨트롤을 없애지 않는다"]
6. **자동 전환은 예고·복원한다.** 앱이 스스로 화면을 바꿀 때는 직후에 출구를 1회 안내하고,
   점프였다면 끝난 뒤 원래 화면으로 되돌린다.

## 4. 제안 — 탭 중심 전역 문법 (to-be)

### 4-1. 전역 제스처 규칙 (P1)

| 화면/상태 | **두 번 탭** (화면 아무 곳) | **길게 누르기 ≈1초 / 시스템 뒤로가기** | 온스크린 버튼 (유지) |
|---|---|---|---|
| 홈 | 세션 시작 | 뒤로 1회차 "한 번 더 누르면 종료" 안내 → 2초 내 재입력 시 종료 | 마이크 원, 사진 찾기, 설정 |
| LISTENING | 발화 종료 | 세션 취소 → 홈 | (홈 UI 유지) |
| AIMING | **셔터** | 세션 취소 → 홈 | 촬영 취소, 셀카 전환 |
| 결과 | 다시 촬영 | 홈 ("사진은 저장됐어요" 1회) | 저장, 다시 촬영, 다시 듣기, 라벨 |
| 설정 / 사진 찾기 | (미할당 — 일반 터치 UI) | 홈 (설정은 서버 주소 적용 포함) | 각 화면 버튼 + 최하단 복귀 |

- **두 번 탭인 이유**: 조준 중 파지 조정·손바닥 접촉으로 인한 오촬영 방지 +
  TalkBack "두 번 탭=실행" 관례와 의미 일치. [추정 — 오탭 방지 효과는 검증]
- **홈·결과처럼 다른 터치 타깃이 있는 화면**에서는 "아무 곳 두 번 탭"이 버튼 단일 탭과
  공존한다: 단일 탭은 버튼에만 반응하고, 빈 영역 두 번 탭이 주 동작이다.
  설정·사진 찾기는 목록·슬라이더 조작이 많아 전면 제스처를 걸지 않는다(오조작 방지).
- **TalkBack 호환**: 전면 제스처 영역을 주 동작 라벨의 단일 접근성 노드로 노출
  (예: AIMING의 미리보기 = "촬영. 두 번 탭하면 사진을 찍습니다"). TalkBack 사용자는
  표준 제스처로, 비사용자는 `detectTapGestures(onDoubleTap)`으로 — 같은 콜백에 수렴.
- **셔터 흔들림 보정**: 탭이든 버튼이든 트리거 행위는 기기를 흔든다. 이미 있는
  `RingFrameBuffer`(전후 1초)+`FrameScorer`로 "트리거 전후 최적 프레임을 채택한다"를
  명시 정책으로 격상한다 — 구현이 이미 있어 비용이 낮다.
- 구현: `BackHandler` 추가, 전면 제스처는 `pointerInput` 레이어. 볼륨 핸들러는 수정하지 않는다.

### 4-2. 볼륨 버튼 전환 계획 (P1과 병행)

| 단계 | 볼륨 버튼 상태 |
|---|---|
| 1. 탭 문법 출시 | 기존 매핑 그대로 병행 (짧게=진행, 길게=취소). 온보딩·안내 문구는 **탭을 먼저, 볼륨을 나중에** 말하도록 교체 |
| 2. 검증 | 탭 셔터 사용률·오조작률·셔터 시점 편차를 로그로 비교. 탭이 열등하지 않으면 다음 단계 |
| 3. 제거 | 볼륨 핸들러 삭제, 볼륨 키는 시스템 볼륨으로 환원(사운드·TTS 크기 조절이 오히려 자연스러워짐) |

- 검증 없이 즉시 제거하지 않는 이유: 물리 버튼 선호 사용자가 존재할 수 있고
  (연구① 선호 다양성), 탭 문법의 실기기 오조작률이 아직 미지수다. [추정]

### 4-3. 전환 확인 3채널 (P1)

- **earcon+햅틱**: "진입"과 "복귀" 2가지 신호(2음 상승=들어감, 하강=홈으로)로 통일.
  화면별로 다른 소리를 만들지 않는다 — 외울 소리는 2개면 충분하고, 어느 화면인지는
  TTS·헤더가 말한다. [추정 — 상승/하강 은유는 검증]
- **TTS 1회**: 진입 시 "설정 화면입니다" / "사진 찾기 화면입니다. 아래에 말해서 찾기 버튼이
  있어요" / 복귀 시 "홈입니다". 첫 진입에만 버튼 위치를 덧붙이고 재진입부터는 이름만.
  [근거 있음 — 연구① "초기에 한 번 충분히 설명" 선호. TalkBack 중첩은 talkback-behavior.md
  미결 쟁점과 함께 확인]
- **시각 헤더**: 모든 위성 화면 상단 같은 위치에 대형 헤더(아이콘+이름, 24sp 이상, 고대비) +
  화면별 배경 톤 차이로 주변시로도 전환을 감지하게 한다. 색만으로 구분하지 않는다.
  [근거 있음 — WCAG 1.4.1, accessibility-guidelines "저시력 시각 정보 병행"]

### 4-4. 배치 문법 통일 (P2)

모든 화면이 같은 세로 골격: **상단 헤더(정체) → 내용 → 하단 주 동작(전폭) → 최하단 복귀(전폭)**.

- **홈**: 설정 진입을 우상단 칩에서 하단으로 — "🖼 사진 찾기 | ⚙ 설정" 2분할 전폭 행
  (각 48dp 이상). 모서리 소형 타깃 제거. 마이크 원의 탭 타깃은 중앙 영역 전체로 확장.
- **사진 찾기**: 좌상단 ‹ 는 유지하되 최하단 전폭 "홈으로" 버튼 추가.
- **설정**: "돌아가기"를 최하단 전폭 대형 버튼으로. 서버 주소 적용 로직을 복귀 경로
  공통부로 이동(뒤로 제스처로 나가도 실행되게).
- **결과**: "저장"(주 동작) 하단 전폭 유지, "다시 촬영"은 그 위.

### 4-5. 자동 전환의 예고와 복원 (P2~P3)

- **결과 진입 직후**: 요약 낭독 끝에 1회 "다시 찍으려면 화면을 두 번 탭,
  끝내려면 뒤로 가기". 자동으로 나타난 화면이므로 출구를 반드시 알려준다.
- **얼굴 등록 점프**: "카메라 화면으로 이동합니다" 예고 → 등록 종료(성공·실패 모두) 후
  **설정으로 자동 복귀** + "설정으로 돌아왔어요". 현재는 카메라 화면에 남겨진다.
- **결과 자동 닫힘은 도입하지 않는다** — 낭독을 들을 시간은 사용자가 정한다.
  [근거 있음 — 촬영 주체성 원칙의 연장]

### 4-6. 세션 레이어 구조는 유지 (변경 없음 명시)

LISTENING/PARSING 동안 홈이 떠 있는 현재 구조는 전환 횟수를 줄이는 좋은 설계라 유지한다.
AIMING 진입 시의 기존 TTS("카메라를 비춰 주세요…")가 이미 전환 확인 역할을 한다.

## 5. 우선순위

| 순위 | 항목 | 이유 |
|---|---|---|
| P1 | 4-1 전역 제스처(특히 AIMING 탭 셔터) + `BackHandler` + 4-3 전환 3채널 + 온보딩 문구 교체 | 촬영 트리거의 탭 이관과 종료 사고 방지가 최우선. 상태 머신은 그대로 두고 트리거·안내만 추가 |
| P2 | 4-4 배치 문법 통일 + 결과 출구 안내 | 레이아웃 수정 범위가 넓지만 로직 변경은 적음 |
| P3 | 4-5 얼굴 등록 문맥 복원, 4-2 볼륨 제거(검증 통과 후) | 빈도 낮은 흐름 / 데이터 확보 후 결정 |

## 6. 검증할 가설

1. 탭 셔터가 볼륨 셔터 대비 셔터 시점 편차를 줄이는가 (편차 로그 정량 비교)
2. 빈 영역 두 번 탭과 버튼 단일 탭의 공존이 오조작 없이 학습되는가
3. "두 번 탭=진행 / 길게·뒤로=복귀" 2문법을 별도 학습 없이 쓰는가
4. 진입/복귀 2종 earcon(상승/하강) 은유가 전달되는가
5. 볼륨 버튼 제거 후 물리 버튼을 아쉬워하는 사용자 비율 (제거 결정의 근거)
6. 전환 TTS가 TalkBack 낭독과 겹치지 않는가 (talkback-behavior.md 미결 쟁점과 동일)
