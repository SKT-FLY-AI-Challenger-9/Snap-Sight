# 전달할 촬영 상태 정리 (초안)

> 문서 상태: 초안 (팀 리뷰 전)
> 관련 이슈: #5 [FE] feature: 접근성 UX 및 햅틱·사운드 피드백 인터페이스 정의
> 선행 문서: docs/research/blind-camera-ux-notes.md, docs/ux/design-principles.md

## 목적

사용자에게 전달해야 할 촬영 상태가 무엇인지 정리한다. 이 문서는 "무엇을 전달해야 하는가"만 다루고, 그것을 하나의 데이터 구조로 어떻게 표현할지(필드명, 타입)나 여러 축이 동시에 발생할 때 어떻게 조합할지는 다루지 않는다 — 각각 4단계, 6단계의 몫이다.

## LEFT/RIGHT/CLOSER/READY/TARGET_LOST는 하나의 상태 목록이 아니라 여러 축이 섞여 있을 수 있다

다섯 후보를 그대로 나열하면 마치 서로 배타적인 한 종류의 값처럼 보이지만, 실제로는 성격이 다른 축들이 섞여 있다.

- **탐지 축**: 피사체를 찾았는가 (TARGET_LOST는 이 축에 속함)
- **수평 축**: 피사체가 목표보다 왼쪽/중앙/오른쪽 어디 있는가 (LEFT/RIGHT는 이 축에 속함)
- **거리 축**: 피사체 크기가 목표보다 작은가/적정한가 (CLOSER는 이 축에 속함, 근거는 약함 — Document A 참고)

이 세 축이 독립적이라는 근거는 Document A에 이미 있다. EasySnap은 위치·크기(%)·기울기를 **각각 따로 측정해 한 메시지에 결합**해서 전달했다 — 즉 원래 구현체에서도 이 값들은 서로 다른 축으로 따로 계산되고, 동시에 다른 값을 가질 수 있는 것으로 다뤄졌다. "피사체가 왼쪽에 있으면서 동시에 너무 멀리 있는" 상황은 실제로 존재할 수 있고, 하나의 값(LEFT 또는 CLOSER)으로는 두 상황을 동시에 표현하지 못한다.

READY는 이 세 축과 층위가 다르다 — "탐지됨 + 수평 허용 범위 + 거리 허용 범위(있다면)를 모두 만족"하는 **합성 조건**이지, 축 자체가 아니다.

**추가 확인(2026-08-14, cothe-baek): 축이 실제로는 4개였다.** ②가 dx뿐 아니라 **dy(수직 편차)도 계산**하고 있다는 게 확인됐다. 즉 애초에 이 문서가 세 축(탐지/수평/거리)만 다룬 것부터가 축소된 그림이었다 — 실제로는 **수직 축**도 존재한다. 다만 dy는 현재 피드백 로직에는 쓰이지 않고 있으며, 반영 시점은 미정이다(cothe-baek 본인의 추측으로는 "오늘 중"이나 확정 아님).

탐지 축의 정의도 구체화됐다: **LOST**는 피사체가 화면에서 사라졌거나 다른 물체에 가려진 경우, **AMBIGUOUS**는 사람은 검출되지만 원하는 타겟인지 특정할 수 없는 경우다. 다만 이 둘을 지금 단계에서 구분해서 다룰지는 아래 "현재 구현 범위"에서 다룬다 — 결론부터 말하면 **당장은 하나로 합쳐서 다뤄도 된다**고 확인됐다.

## 축별 후보 신호, 근거 강도, 현재 구현 범위

"선행연구 근거"(Document A 기준, 바뀌지 않음)와 "현재 구현 범위"(cothe-baek 확인, 팀의 실제 결정)는 서로 다른 종류의 정보라 열을 분리했다. 참고: 아래 표의 "연구②·⑤"는 Document A의 논문 번호이고, 팀 역할 "②(cothe-baek)"와는 다른 표기다 — 혼동하지 않도록 구분해서 적었다.

| 축 | 후보 신호 | 선행연구 근거 강도 (Document A) | 현재 구현 범위 (cothe-baek 확인, 2026-08-14) |
|---|---|---|---|
| 탐지 | LOST / AMBIGUOUS (TARGET_LOST의 세분화) | 약함 — 전용 피드백 패턴을 설계한 선행 사례 없음 | 정의 구체화됨(화면이탈·가려짐 / 타겟 특정 실패). **당장은 하나로 합쳐서 처리** |
| 수평 | LEFT / RIGHT | 강함 — 연구②, 연구⑤ 모두 직접 근거 | **dx 제공됨, 지금 사용** |
| 수직 (신규) | 후보 미정 (가칭 UP/DOWN) | Document A는 이 축 자체를 다루지 않음 — 근거 없음 | dy는 계산되지만 **현재 미사용**, 반영 시점 미정 |
| 거리 | CLOSER | 가장 약함 — 실시간 거리 안내를 이산 상태로 만든 선행 사례 없음 | 당장 미구현, 확장성만 고려 |
| 합성 | READY | 중간 — 연구②에서 문장 단위 직접 근거 1건 | 탐지+수평 기준으로 잠정 정의 (거리·수직 미포함) |

## 지금 실제로 구현되는 것 (우리의 해석 → cothe-baek 확인으로 갱신됨)

원래는 근거 강도 순으로 우선순위를 추정했었는데, cothe-baek 확인 결과 실제 구현 범위가 그 추정과 상당 부분 일치했다.

1. **탐지 여부** — 다른 모든 안내의 전제 조건. 실제로 지금은 LOST/AMBIGUOUS를 하나로 합쳐서 다룬다(확인됨).
2. **수평 편차** — 근거가 가장 강했고, 실제로 지금 dx가 제공되어 사용 중이다(확인됨).
3. **READY 여부** — 근거는 중간이었고, 지금은 탐지+수평만으로 잠정 정의된다(거리 미포함, 확인됨).
4. **거리 편차(CLOSER)** — 근거가 가장 약했고, 실제로도 당장 구현 안 하기로 확인됐다. 추정이 맞아떨어진 경우다.

**수직 편차(dy)는 이 목록에 없던 항목이다.** 근거 강도 순위와 무관하게 계산 자체는 이미 되고 있고(피드백 반영 여부만 미정), 이 우선순위 추론 방식으로는 예측하지 못했던 부분이다.

즉 이 목록은 더 이상 "우리의 잠정 판단"만이 아니라 **실제 구현 범위와 일치가 확인된 부분(1~4)**과 **추론 밖에 있었던 부분(수직)**으로 나뉜다. "동시에 여러 축이 발생했을 때 무엇을 먼저 보여줄지"는 여전히 Document F(6단계) 몫이다.

## 아직 결정하지 않은 것

- 위 신호들을 하나로 합친 값(enum)으로 표현할지, 축별로 분리된 값으로 표현할지 — 판정 로직이 ⑥ 담당이라는 건 확인됐지만, 그 결과를 어떤 자료구조로 표현할지는 여전히 미정
- 수직 축(dy)을 언제 도입할지, 도입하면 어떤 후보 신호(예: UP/DOWN)를 추가할지
- LOST/AMBIGUOUS를 나중에 분리하게 될 시점과 조건
- 축이 동시에 여러 개 벗어났을 때 무엇을 먼저/함께 전달할지 (→ 6단계, Document F에서 일부 다룸)

## 이 문서에서 다루지 않는 것

- ②↔⑥ 데이터 계약 (필드명, 타입, 프로토콜) — Document D 참고
- 상태별 햅틱·사운드·TalkBack 매핑 — Document E 참고
- 동시 상태의 결합·우선순위·충돌 처리 규칙 — Document F 참고
