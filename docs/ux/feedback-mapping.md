# 상태별 햅틱·사운드·TalkBack 피드백 매핑 (초안)

> 문서 상태: 초안 (팀 리뷰 전)
> 관련 이슈: #5 [FE] 접근성 UX 및 햅틱·사운드 피드백 인터페이스 정의
> 선행 문서: docs/research/blind-camera-ux-notes.md, docs/ux/design-principles.md, docs/ux/capture-states.md, docs/interfaces/cv-to-ux-interface-draft.md

## 목적

Document C의 축(탐지/수평/거리, READY)을 실제 피드백 채널(햅틱/사운드/TalkBack)에 매핑한다. 이 문서는 "어떤 채널로, 어떤 성격의 신호를 줄지"까지만 다루고, 정확한 수치(진동 강도, 지속시간, 주파수)는 확정하지 않는다 — 프로토타입 단계(7단계)에서 튜닝한다. 여러 축이 동시에 발생했을 때 어떻게 합칠지는 다루지 않는다 (→ 6단계).

## 채널 구분

- **사운드**: 앱이 자체적으로 재생하는 비언어 소리(톤, 신호음 등) — 연속·반복 재생에 사용
- **TTS**: 앱이 자체적으로 재생하는 음성 문구 — **주요 상태 변화 시 1회**만 사용, 반복 재생하지 않음 [정책, 2026-08-19]
- **TalkBack**: OS 스크린리더. 화면 요소 탐색용이며, Document B 원칙 2에 따라 TTS와 동시에 말하지 않게 설계한다
- **햅틱**: 폰의 진동 모터 1개 (여러 축을 동시에 표현하기 어려운 채널)

### 사운드/TTS 분리 정책 [신규 결정, 2026-08-19]

기존에는 "사운드"에 짧은 음성 문구까지 포함해서, LEFT/RIGHT 같은 연속 안내에도 음성이 반복 재생될 수 있었다. 이를 명확히 분리한다.

- **연속 피드백(LEFT/RIGHT/CLOSER/FARTHER)은 사운드·햅틱(비언어)로만** 전달한다 — 음성 문구를 반복 재생하지 않는다
- **주요 상태 변화(READY/LOST)만 TTS로 1회** 안내한다
- 선행연구② ·⑤는 음성 문구를 연속 안내에도 썼지만, 선행연구④(PMC)는 방향 안내를 톤+진동만으로 처리했다 — 이 정책은 선행연구④의 방식을 채택한 것이며, 기존에 확정된 규칙을 뒤집는 게 아니라 근거가 갈리던 지점에서 하나를 선택한 것이다

## 매핑

### 수평 편차 (LEFT / RIGHT 후보)
근거 강도: 강함 (Document A) · **현재 구현 범위: 확정, dx로 실제 제공됨(cothe-baek 확인, 2026-08-14) — 지금 유일하게 활성화된 축**

- **사운드** [근거 있음, 채널은 정책으로 조정됨] 방향을 알리는 비언어 신호(톤 등)로 연속 재생. 다른 축과 동시 발생 시 하나의 신호로 결합하는 형태를 우선 검토 — 원래 근거(Document B 원칙 4)는 음성 채널 실험이었지만, 사운드/TTS 분리 정책에 따라 이 축은 비언어 사운드로 구현한다
- **햅틱** [추정] 진동 모터 1개로 "왼쪽/오른쪽"을 구분하는 패턴에 대한 직접 근거는 없음. 패턴 길이·간격 차이 등을 후보로 검토할 수 있으나 검증되지 않음
- **TTS** 사용하지 않음 (연속 피드백이므로 사운드/TTS 분리 정책 대상)
- **TalkBack** 원칙 2(중첩 방지) 적용 대상

### READY (탐지+수평 — 합성 조건, 거리·수직은 미포함으로 확정)
근거 강도: 중간 (Document A)

- **TTS** [근거 있음] "지금 촬영 가능"을 알리는 명확한 완료 신호, **주요 상태 변화이므로 1회만 재생**. 연구②(Document A)에서 "가운데 구도가 맞습니다. 사진을 촬영해 주세요"라는 직접 근거 있음
- **햅틱** [추정] 다른 상태와 확실히 구분되는 고유 패턴이 필요해 보이나 구체적 형태는 미검증
- READY가 거리 축을 포함하는지는 Document C에서 열린 문제였는데, **cothe-baek 확인으로 "탐지+수평만 만족"이 현재 범위로 확정됐다**(거리·수직 미반영이므로 자동으로 제외됨)

### 탐지 축 (LOST / AMBIGUOUS)
근거 강도: 약함 (Document A) · **현재 구현 범위: 확정, 당장은 하나로 합쳐서 처리 (cothe-baek 확인, 2026-08-14)**

- LOST(화면 이탈·가려짐)와 AMBIGUOUS(타겟 특정 실패)를 구분해서 다른 피드백을 줄지 열려 있었는데, **당장은 구분하지 않고 하나의 "탐지 실패" 상태로 합쳐서 처리**하는 것으로 확인됐다. 나중에 두 상태가 실제로 분리되면 이 절도 다시 나눠야 한다.
- **TTS** [약한 근거] 탐지 실패도 상태 변화이므로 1회 안내 대상. EasySnap의 "Searching" 알림 정도가 유일한 선행 사례
- **햅틱** [추정] 선행 사례 없음

### 거리 편차 (CLOSER / FARTHER)
근거 강도: 가장 약함 (Document A/B/C에서 일관됨) · **현재 구현 범위: `size_deviation`으로 계산 예정 (`docs/deviation-interface.md` v0.1, 이슈 #29 완료 대기)**

**매핑 대상으로 전환.** 선행연구 근거는 여전히 약하지만, 실제 데이터(`size_deviation`)가 곧 제공될 예정이라 더 이상 "구현 자체가 없어서" 보류할 이유가 없다. 수평 편차와 동일한 방식(연속 피드백이므로 **사운드**(비언어)+햅틱, TTS 미사용)으로 매핑을 준비한다.

### landscape 세션 정책 [확정, 2026-08-17]

`subjectType=landscape`(피사체 없는 풍경 등) 세션에서는 **편차(수평·거리) 피드백을 주지 않는다.**

- landscape는 데이터상 "탐지 실패(LOST)"와 동일하게 `detection=None`으로 전달되지만, 의미가 다르다 — LOST는 "찾다가 놓친 것", landscape는 "애초에 조준 대상이 없는 것"이다. LOST와 같은 "찾는 중" 피드백을 주면 사용자에게 혼란을 준다.
- `subjectType`은 세션 시작 시점(발화 파싱 결과)에 이미 알 수 있으므로, 프레임마다 판단할 필요 없이 세션 시작 시 한 번에 결정한다.

### 수직 편차 (신규 — Document C에 새로 추가된 축)
근거 강도: 없음 (Document A는 이 축 자체를 다루지 않음) · **현재 구현 범위: dy는 계산되지만 피드백에는 미반영. 반영 시점 미정(cothe-baek 추측으로는 "오늘 중"이나 미확정)**

**매핑하지 않는다.** CLOSER와 마찬가지로 아직 매핑 대상이 아니다. 다만 CLOSER와 성격이 다르다 — CLOSER는 "근거가 약해서" 보류된 것이고, 수직은 "이미 계산은 되는데 아직 피드백 로직에 연결 안 됨"이라 더 빨리 매핑이 필요해질 수 있다. dy 반영이 확정되면 이 절을 우선적으로 채워야 한다.

## 아직 매핑하지 않은 것

- CLOSER/FARTHER(거리) 실제 매핑 — 데이터는 곧 제공되나 구체적 문구·패턴은 미정
- 수직(y축) 매핑 — 계약 v0.2 예정, 그전까지 보류
- 정확한 수치(진동 강도, 지속시간, 사운드 주파수) — 프로토타입에서 튜닝

- 실제 Kotlin 구현 (→ 7단계)
