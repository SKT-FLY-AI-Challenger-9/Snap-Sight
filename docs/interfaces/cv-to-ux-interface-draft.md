# ②↔⑥ 인터페이스 범위 정의 (제안)

> 문서 상태: 제안 — ② 담당자(cothe-baek) 검토 전, 계약 아님
> 관련 이슈: #5 [FE] 접근성 UX 및 햅틱·사운드 피드백 인터페이스 정의, #2 [AI] 온디바이스 객체 탐지 및 추적 모듈 구현
> 선행 문서: docs/research/blind-camera-ux-notes.md, docs/ux/design-principles.md, docs/ux/capture-states.md

## 담당자 확인

편차 관련 원시 수치(dx/dy) 계산은 팀 내에서 ②(cothe-baek, 이슈 #2) 담당으로 합의되었다. cothe-baek이 아래 질문들에 구체적으로 답변한 것으로 보아 실질적으로는 확인된 것으로 본다. **다만 이슈 #2 본문("범위 제외: 편차 계산과 햅틱·사운드 피드백은 담당 모듈 범위로 분리")과 README 역할표는 아직 이 내용을 반영하도록 수정되지 않았다** — "역할 자체를 공식적으로 재확인하고 문서를 고칠지"는 별도로 확인이 필요한 항목으로 남겨둔다 (아래 "여전히 열려있는 것" 참고).

## 실제 코드 확인 결과 (2026-08-14, `dev` 브랜치 `docs/android-cv-module.md` 기준)

cothe-baek의 구두 답변(아래 "cothe-baek 답변" 절) 이후 ②의 실제 구현이 `dev`에 merge됐다. **실제 계약은 구두 답변보다 훨씬 구체적이고, 일부는 다르다.**

### 실제 JSON 계약
```json
{
  "objects": [
    { "track_id": 17, "label": "person", "confidence": 0.94,
      "bbox": { "x_min": 0.31, "y_min": 0.12, "x_max": 0.68, "y_max": 0.91 } }
  ]
}
```
"dx 하나"가 아니라 **탐지된 모든 객체의 목록**(track_id·라벨·신뢰도·bbox)이 매 프레임 나온다.

### 실제 파이프라인
```
탐지(모든 객체) → TargetSelector(현재 pass-through, ①STT 연동 대기) → DeviationCalculator(현재 no-op) → 출력
```

**`DeviationCalculator`는 아직 아무도 구현하지 않은 확장 자리다.** `cv/` 패키지(②의 폴더) 안에 인터페이스만 정의되어 있고, 기하 원시값(`BoundingBox.centerX/centerY/area`)은 계약에 있지만 이걸로 편차를 계산하는 로직은 비어 있다. **즉 지금 시점에 dx/dy는 실제로 계산되고 있지 않다** — 아래 "cothe-baek 답변"에서 "dx는 확정, 지금 사용"이라고 적었던 부분은 정정이 필요하다.

### 새로 생긴 질문: DeviationCalculator는 누가 구현하나
`cv/` 폴더(②) 안에 있지만 구현 주체가 문서에 명시되어 있지 않다. cothe-baek의 "판정은 ⑥이 한다"는 답변과 이 코드 구조가 어떻게 맞물리는지 확인이 필요하다 — ⑥이 이 클래스를 구현해서 ②의 폴더에 끼워 넣는 건지, ②가 구현하고 결과만 ⑥에 넘기는 건지 아직 불명확하다.

### 확인된 것 (그대로 유효)
- 온디바이스, 같은 프로세스 (README "③ 백엔드가 편차 계산" 원안은 지연시간 때문에 폐기됐다고 코드 문서에 명시됨)
- 프레임 스킵 시에도 직전 결과를 `analyzed=false`로 계속 내보냄 — "⑥ 피드백 루프가 끊기지 않게" 하기 위함이라고 명시. Document B 원칙 3(고정 주기 갱신)이 실제로 반영된 설계
- `CaptureSessionManager`가 AIMING 상태 진입 시 `cv.startNewSession()` 호출 — 세션 상태 매핑 확인됨
- 실기기 p50/p95 지연시간은 여전히 미측정

## 이슈 #18(원준서, ⑤→③ 제안)과의 충돌 및 UX 근거

`docs/detection-api-design.md`(이슈 #18)는 **③(백엔드)이 네트워크 API로 판정하는 구조**(`POST /api/judge/aim`, 왕복 지연 예산 200ms)를 제안하고 있다. 이는 이 문서의 "온디바이스, ⑥이 판정" 결론과 정면으로 다르다. 이슈 #18에 조율을 요청하기 전에, 저희(⑥) 쪽 근거를 먼저 정리한다.

### 근거 1: 레이턴시 계산

- 이슈 #18 자체 예산: 네트워크 왕복 **200ms**
- 온디바이스 추론만으로도 이미 p95 ~80ms(PC 기준, cothe-baek 측정, 안드로이드 기기 미측정)가 드는데, 여기에 200ms를 더하면 총 280ms 이상 — 사용자가 카메라를 움직이는 동안 응답이 눈에 띄게 늦어질 수 있는 수준
- Document A에서 검토한 실시간 조준 가이드 선행연구 2편(②, ⑤ 논문) 중 네트워크 왕복을 쓴 사례는 없음 — 전부 온디바이스로 구현됨. 즉 "실시간 조준 피드백은 온디바이스"라는 방향이 우리만의 판단이 아니라 선행연구 전반의 패턴과도 일치

### 근거 2: ②(cothe-baek) 본인의 기존 문서와도 어긋남

`docs/android-cv-module.md`(② 본인이 작성)에 이미 이렇게 적혀 있다:

> "리드미 원안은 ③ 백엔드가 편차를 계산하지만, 매 프레임 bbox를 서버까지 왕복시키면 햅틱 피드백 지연을 감당할 수 없다. 그래서 편차는 CV와 같은 온디바이스 프로세스에 두되..."

즉 이슈 #18의 제안은 저희와 어긋날 뿐 아니라, **②(cothe-baek) 본인이 이미 명시적으로 배제했던 방식과도 어긋난다.** 이건 저희와 원준서님 사이의 조율만이 아니라, ②·⑤·⑥ 세 역할 간 조율이 필요하다는 뜻이다.

### 근거 3: 신뢰성 (README 핵심 가치와의 연결)

README는 "시각장애인이 다른 사람의 도움 없이 독립적으로 촬영"하는 것을 핵심 가치로 명시한다. 실시간 조준 안내가 네트워크 연결에 의존하면, 연결이 불안정하거나 끊긴 순간 안내 자체가 멈춘다 — 접근성 기능이 네트워크 상태에 따라 사라지는 건 이 핵심 가치와 어긋난다.

### 근거 4: 판정 주체 합의 이력

cothe-baek이 이미 구두로 "판정 로직은 ⑥ 담당"이라고 확인했다(2026-08-14, 이 문서 상단 "cothe-baek 답변" 절). 이슈 #18의 제안(③이 판정)은 이 합의와도 다르다. 다만 이 구두 합의도 이슈 #2 본문에 공식 반영은 안 된 상태였으므로, 완전히 "확정된 사실을 뒤집는다"고 말하긴 어렵다 — 오히려 팀 전체적으로 이 결정이 아직 뿌리내리지 못했다는 신호로 보는 게 정확하다.

### 결론 (제안)

위 네 가지 근거로, 이슈 #18에는 "네트워크 API 방식 대신 온디바이스+⑥판정 방식을 재검토해달라"는 요청을 하려 한다. 다만 최종 결정권은 저희 혼자에게 있지 않으므로, 근거 제시 후 ②·③(있다면)·⑤와 함께 조율하는 방향으로 제안한다.

## 아키텍처 함의: 이건 네트워크 API가 아니라 같은 프로세스 내부 인터페이스일 가능성이 높다

README에 따르면 ②의 산출물은 ⑤가 관리하는 Android 프로세스 안에서 실행된다. ⑥도 같은 Android 앱의 역할이다. 즉 편차 관련 원시 수치까지 ②가 맡는다면, ②→⑥으로 데이터가 넘어가는 경로는 서버 API 호출이 아니라 **같은 앱 프로세스 안의 함수 호출/인메모리 데이터 전달**일 가능성이 크다.

**cothe-baek 확인 결과(2026-08-14): "앱 프로세스 안의 함수 호출"이라는 답을 받았으나, 본인도 "...?"로 표현할 만큼 확신도가 낮다.** 방향은 맞는 것으로 보이나 완전히 확정된 사실로 취급하지 않는다.

이 방향이 맞다면, 처음에 논의했던 "GuidanceState를 Kotlin 데이터 구조로 설계"라는 접근과 자연스럽게 맞는다 — 네트워크 페이로드가 아니라 인메모리 객체로 설계하면 된다는 뜻이다. 다만 실제 구현 언어(Kotlin 여부)는 별개로 미확정 상태다.

또한 판정 로직(임계값 적용, LEFT/RIGHT/READY 등으로 분류하는 것) 자체는 ⑥이 담당하는 것으로 구두 확인됐다(질문 1 답변). 다만 실제 코드 기준으로는 ②가 "원시 dx"를 주는 게 아니라 **객체 목록(bbox 포함)을 주고, 그걸 dx로 바꾸는 단계(DeviationCalculator) 자체가 비어 있다** — 아래 "실제 코드 확인 결과" 절 참고.

## 실제 문서화된 ②의 출력 (`docs/android-cv-module.md`, 2026-08-14 코드 기준 — 이 부분이 확정)

- 프레임마다 탐지된 **모든 객체**의 목록: `track_id`, `label`, `confidence`, 정규화된 `bbox`(x_min/y_min/x_max/y_max)
- 위 항목들을 `CvFrameOutput.objectsJson()`으로 Android(⑤) 프로세스 안에서 직접 전달 (이슈 #2 본문의 "TrackingOutput"이라는 이름은 실제 코드에는 없음 — 옛 계획 문서 표현)
- 편차(dx/dy/거리)는 `CvFrameOutput.deviation` 필드로 나갈 예정이지만, 계산 로직(`DeviationCalculator`) 자체가 아직 no-op

## Document C의 축과 ②의 기존 출력 매핑

| Document C 축 | ②의 출력 (2026-08-14 코드 확인 기준) | 상태 |
|---|---|---|
| 탐지 축 | `objects: []` (빈 배열 = 탐지 실패로 추정, 명시적 LOST/AMBIGUOUS 필드는 코드에 없음) | 구두로는 "정의 구체화, 당장 하나로 합침"이라 들었으나 실제 계약엔 이 개념이 아직 없음 — 재확인 필요 |
| 수평 축 (원시 값) | **미구현.** bbox의 `centerX`는 있으나, 이를 dx로 변환하는 `DeviationCalculator`가 no-op | 누가 구현하는지도 미정 (⑥ vs ②) |
| 수직 축 (원시 값) | 마찬가지로 미구현 (`centerY`는 있음) | 위와 동일 |
| 거리 축 (크기 비율) | `area`는 계약에 있으나 미사용, `DeviationCalculator` 미구현이라 여기 포함 여부도 아직 결정 안 됨 | 확장성만 고려하기로 구두 확인됐던 내용은 유효 |

LOST와 AMBIGUOUS는 cothe-baek의 구두 정의("화면 이탈/가려짐" vs "사람은 보이나 원하는 타겟인지 불확실")는 유효하지만, **실제 코드의 JSON 계약에는 이 두 상태에 대응하는 명시적 필드가 없다.** `objects: []`(빈 배열)를 탐지 실패로 볼 수 있을지, AMBIGUOUS는 `TargetSelector`(현재 pass-through) 쪽에서 다뤄질지는 재확인이 필요하다.

## cothe-baek 답변 (2026-08-14 구두 확인 — 위 "실제 코드 확인 결과" 절 참고)

아래는 구두로 확인했던 내용이다. 이후 실제 코드를 보니 "판정은 ⑥, dx 원시값 제공"이라는 큰 방향은 맞지만, **dx가 이미 계산되어 나오고 있다는 부분은 아직 사실이 아니다** — DeviationCalculator가 no-op이기 때문이다. 나머지 답변은 유효하다.

| # | 질문 | 답변 |
|---|---|---|
| 1 | 판정까지 하는지, 원시 값만 주는지 | **원시 값(dx)만 제공, 판정(카테고리화)은 ⑥ 담당** |
| 2 | 거리/크기 편차 계산 가능한지 | **당장 미구현.** 번거로워서 보류, 확장성만 고려해 설계. 대신 dx뿐 아니라 **dy(수직)도 계산됨** — 새로 확인된 사실 |
| 3 | LOST/AMBIGUOUS 구분 필요한지 | LOST=화면 이탈·가려짐, AMBIGUOUS=사람은 보이나 원하는 타겟인지 불확실. **당장 구현 안 함, 하나로 합쳐도 됨**, 확장성만 고려 |
| 4 | 갱신 주기 | **PC 기준** p95 지연 ~80ms, FPS ~11, 모델 미최적화. 3프레임마다 계산하는 방안 검토 중. 안드로이드 기기 기준 수치는 아직 없음 |
| 5 | 다축 동시 처리 | **당장은 수평(dx) 편차만 고려.** 거리는 확장성만. dy 반영 여부는 미정 |
| 6 | 전달 방식 | 같은 앱 프로세스 내 함수 호출로 추정되나, 본인 확신도 낮음 |

## 여전히 열려있는 것

- **`DeviationCalculator`를 누가 구현하는지** (신규, 가장 시급함) — ⑥이 구현해서 `cv/` 폴더에 끼워 넣는 건지, ②가 구현하는 건지 코드·문서 어디에도 명시 안 됨
- **탐지 실패(LOST/AMBIGUOUS) 표현 방식** — 코드 계약엔 명시적 필드가 없음. `objects: []`로 볼지, 별도 필드가 추가될지 확인 필요
- **dy(수직 편차)가 언제, 어떻게 피드백에 반영될지** — "오늘 중 될 것 같다"는 cothe-baek 본인의 추측이었고, 애초에 dy 자체도 DeviationCalculator 미구현 상태라 더 불확실해짐
- **역할 재확인의 공식화 여부** — 이슈 #2 본문("범위 제외")과 README 역할표를 실제로 고칠지는 아직 안 물어봤다 (여전히 "③ 백엔드"라는 표현이 `docs/android-cv-module.md`에도 남아있음)
- **전달 방식(질문 6)의 확정** — cothe-baek 본인도 확신이 낮았으나, 실제 코드(같은 앱 프로세스 내 `SnapSightFrameProcessor` 콜백)로 보면 이 부분은 사실상 확인된 것으로 봐도 될 듯
- **안드로이드 기기 기준 지연시간/FPS** — `docs/android-cv-module.md`에도 "아직 측정하지 않았다"고 명시됨, 여전히 미해결
