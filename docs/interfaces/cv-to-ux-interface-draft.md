# ②↔⑥ 인터페이스 범위 정의 (제안)

> 문서 상태: 제안 — ② 담당자(cothe-baek) 검토 전, 계약 아님
> 관련 이슈: #5 [FE] 접근성 UX 및 햅틱·사운드 피드백 인터페이스 정의, #2 [AI] 온디바이스 객체 탐지 및 추적 모듈 구현
> 선행 문서: docs/research/blind-camera-ux-notes.md, docs/ux/design-principles.md, docs/ux/capture-states.md

## 담당자 확인

편차 관련 원시 수치(dx/dy) 계산은 팀 내에서 ②(cothe-baek, 이슈 #2) 담당으로 합의되었다. cothe-baek이 아래 질문들에 구체적으로 답변한 것으로 보아 실질적으로는 확인된 것으로 본다. **다만 이슈 #2 본문("범위 제외: 편차 계산과 햅틱·사운드 피드백은 담당 모듈 범위로 분리")과 README 역할표는 아직 이 내용을 반영하도록 수정되지 않았다** — "역할 자체를 공식적으로 재확인하고 문서를 고칠지"는 별도로 확인이 필요한 항목으로 남겨둔다 (아래 "여전히 열려있는 것" 참고).

## 아키텍처 함의: 이건 네트워크 API가 아니라 같은 프로세스 내부 인터페이스일 가능성이 높다

README에 따르면 ②의 산출물은 ⑤가 관리하는 Android 프로세스 안에서 실행된다. ⑥도 같은 Android 앱의 역할이다. 즉 편차 관련 원시 수치까지 ②가 맡는다면, ②→⑥으로 데이터가 넘어가는 경로는 서버 API 호출이 아니라 **같은 앱 프로세스 안의 함수 호출/인메모리 데이터 전달**일 가능성이 크다.

**cothe-baek 확인 결과(2026-08-14): "앱 프로세스 안의 함수 호출"이라는 답을 받았으나, 본인도 "...?"로 표현할 만큼 확신도가 낮다.** 방향은 맞는 것으로 보이나 완전히 확정된 사실로 취급하지 않는다.

이 방향이 맞다면, 처음에 논의했던 "GuidanceState를 Kotlin 데이터 구조로 설계"라는 접근과 자연스럽게 맞는다 — 네트워크 페이로드가 아니라 인메모리 객체로 설계하면 된다는 뜻이다. 다만 실제 구현 언어(Kotlin 여부)는 별개로 미확정 상태다.

또한 판정 로직(임계값 적용, LEFT/RIGHT/READY 등으로 분류하는 것) 자체는 ⑥이 담당하는 것으로 확인됐다(질문 1 답변) — ②는 원시 dx(및 dy, 현재는 미사용)만 제공한다. 즉 이 인터페이스가 넘기는 건 "판정 결과"가 아니라 "판정 전 원시 값"이다.

## 이미 문서화된 ②의 출력 (이슈 #2 기준 — 이 부분은 확정)

- 정규화된 bbox 위치·크기
- 객체 클래스, confidence
- session-scoped trackId, temporal tracking
- **LOST, AMBIGUOUS, 재탐색 상태 처리**
- 위 항목들을 "TrackingOutput" 형식으로 정의해 Android(⑤)에 인계

## Document C의 축과 ②의 기존 출력 매핑

| Document C 축 | ②의 출력 (2026-08-14 확인 기준) | 상태 |
|---|---|---|
| 탐지 축 | LOST(화면 이탈·가려짐), AMBIGUOUS(타겟 특정 실패) | 정의는 구체화됨. **당장은 구현 안 하고 하나로 합쳐 다뤄도 된다고 확인** — 향후 확장 시 분리 |
| 수평 축 (원시 값) | **dx (확정, 지금 사용)** | ②가 원시 수치로 제공, 판정은 ⑥이 함 |
| 수직 축 (원시 값) | **dy (계산은 됨, 현재 피드백엔 미사용)** | Document C에 없던 축. 오늘 중 추가 가능성 있다고 들었으나 미확정 — "여전히 열려있는 것" 참고 |
| 거리 축 (크기 비율) | 없음, 당장 구현 안 함 | 확장성만 고려하기로 확인됨 |

LOST와 AMBIGUOUS는 정의는 확인됐지만("화면 이탈/가려짐" vs "사람은 보이나 원하는 타겟인지 불확실"), 지금 단계에서는 구분하지 않고 하나의 "탐지 실패" 상태로 합쳐 다뤄도 된다고 확인했다.

## cothe-baek 답변 (2026-08-14 확인)

| # | 질문 | 답변 |
|---|---|---|
| 1 | 판정까지 하는지, 원시 값만 주는지 | **원시 값(dx)만 제공, 판정(카테고리화)은 ⑥ 담당** |
| 2 | 거리/크기 편차 계산 가능한지 | **당장 미구현.** 번거로워서 보류, 확장성만 고려해 설계. 대신 dx뿐 아니라 **dy(수직)도 계산됨** — 새로 확인된 사실 |
| 3 | LOST/AMBIGUOUS 구분 필요한지 | LOST=화면 이탈·가려짐, AMBIGUOUS=사람은 보이나 원하는 타겟인지 불확실. **당장 구현 안 함, 하나로 합쳐도 됨**, 확장성만 고려 |
| 4 | 갱신 주기 | **PC 기준** p95 지연 ~80ms, FPS ~11, 모델 미최적화. 3프레임마다 계산하는 방안 검토 중. 안드로이드 기기 기준 수치는 아직 없음 |
| 5 | 다축 동시 처리 | **당장은 수평(dx) 편차만 고려.** 거리는 확장성만. dy 반영 여부는 미정 |
| 6 | 전달 방식 | 같은 앱 프로세스 내 함수 호출로 추정되나, 본인 확신도 낮음 |

## 여전히 열려있는 것

- **dy(수직 편차)가 언제, 어떻게 피드백에 반영될지** — "오늘 중 될 것 같다"는 cothe-baek 본인의 추측이지 확정 일정이 아니다. 확정되면 Document C(축 분해)에 수직 축을 추가해야 한다
- **역할 재확인의 공식화 여부** — 이슈 #2 본문("범위 제외")과 README 역할표를 실제로 고칠지는 아직 안 물어봤다
- **전달 방식(질문 6)의 확정** — cothe-baek 본인도 확신이 낮으므로 완전히 결정된 사실로 취급하지 않는다
- **안드로이드 기기 기준 지연시간/FPS** — 지금 수치는 PC 기준이라 실제 기기에서 재측정 필요
