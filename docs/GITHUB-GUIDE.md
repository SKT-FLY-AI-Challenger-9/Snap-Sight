# AI 도구로 GitHub 협업하기

**대상**: Git·GitHub를 잘 모르는 사람.
**전제**: Claude Code나 Codex 같은 **AI 코딩 도구 하나**가 있다.

특정 프로젝트에 묶이지 않은 일반 안내입니다. 프로젝트마다 다른 규칙(제목 형식, 라벨 이름 등)은
그 저장소의 문서를 따르세요.

---

## 1. 5분이면 되는 개념

| 용어 | 뜻 | 비유 |
|---|---|---|
| 저장소(repository) | 프로젝트 파일 전체 + 변경 기록 | 문서 폴더 하나 |
| 커밋(commit) | 변경사항을 기록으로 남기는 것 | "여기까지 저장" 스냅샷 |
| 브랜치(branch) | 남에게 영향 없이 따로 작업하는 사본 | 원본 놔두고 뜬 사본 |
| push | 내 컴퓨터의 커밋을 GitHub로 올리기 | 업로드 |
| PR(Pull Request) | "내 브랜치를 원본에 합쳐주세요" 요청 | 검토 요청서 |
| 이슈(issue) | 할 일·버그를 적어두는 글 | 작업 티켓 |
| 머지(merge) | 검토 끝난 브랜치를 원본에 합치기 | 반영 |

핵심은 하나입니다. **원본을 직접 고치지 않고, 사본에서 고친 뒤 검토받고 합칩니다.**
그래서 실수해도 원본이 안 망가집니다.

---

## 2. 딱 한 번만 하는 준비

```bash
git --version     # 없으면 https://git-scm.com
gh --version      # 없으면 https://cli.github.com
gh auth login     # GitHub 로그인 (한 번만)
gh auth status    # "Logged in" 이 뜨면 성공
```

프로젝트 받아오기:

```bash
git clone <저장소 주소>
cd <폴더명>
```

---

## 3. 하루 작업 흐름

```
① 이슈 확인/생성 → ② 최신 코드 받기 → ③ 브랜치 만들기
→ ④ 작업(AI와 함께) → ⑤ 확인 → ⑥ 커밋 → ⑦ push → ⑧ PR
```

### ① 이슈

할 일을 글로 먼저 남깁니다. 브랜치 이름에 이슈 번호를 넣는 팀이 많아서, 보통 이게 먼저입니다.

```bash
gh issue list                 # 이미 있는지 보기
gh issue create               # 새로 만들기 (제목·본문을 물어봅니다)
```

만든 뒤 **번호**(예: `#52`)를 기억하세요.

### ② 최신 코드 받기

작업 시작 전에 항상. 이걸 건너뛰면 나중에 충돌이 납니다.

```bash
git checkout develop      # 팀의 기본 브랜치 이름 (main일 수도 있음)
git pull
```

### ③ 브랜치 만들기

```bash
git checkout -b "feature/#52-login-screen"
```

이름 규칙은 팀마다 다릅니다. 번호에 `#`이 들어가면 **따옴표로 감싸세요.**

### ④ 작업

AI 도구에게 시킵니다. 5절 참고.

### ⑤ 확인 — 커밋 전에 반드시

```bash
git status            # 뭐가 바뀌었나
git diff              # 내용이 어떻게 바뀌었나
```

`git status`에 **내가 안 만진 파일**이나 **모르는 파일**이 있으면 멈추고 확인하세요.

### ⑥ 커밋

```bash
git add <파일 또는 폴더>       # 기록할 것만 고르기
git commit -m "메시지"
```

- **한 커밋에 하나의 의도.** 여러 가지를 했으면 나눠서 여러 번
- `git add .` 는 편하지만 위험합니다. 의도 안 한 파일까지 들어갑니다

### ⑦ push

```bash
git push -u origin "feature/#52-login-screen"
```

### ⑧ PR

```bash
gh pr create --base develop
```

본문에 `close #52` 를 넣으면 머지될 때 이슈가 자동으로 닫힙니다.
그 뒤엔 리뷰를 기다리고, 수정 요청이 오면 같은 브랜치에서 고쳐 다시 커밋·push 하면 PR에 자동
반영됩니다.

---

## 4. 이것만 외우면 됩니다

```bash
git status                 # 지금 상태 (제일 자주 씁니다)
git diff                   # 뭐가 바뀌었나
git add <파일>              # 기록할 것 고르기
git commit -m "메시지"      # 기록
git push                   # 올리기
git pull                   # 받기
git log --oneline -10      # 최근 기록 10개
git checkout -b <이름>      # 새 브랜치
git branch                 # 지금 어느 브랜치인지
```

막히면 **`git status` 부터** 치세요. 대부분 여기에 답이 있습니다.

## 5. AI 도구에게 시키는 법

### 기본 원칙

**한 번에 하나씩, 결과를 보고 다음으로.** "알아서 다 해줘"가 제일 위험합니다. 뭘 했는지 모른 채
커밋하게 되니까요.

### 그대로 써도 되는 문장들

작업 시작:
```
이 저장소의 규칙 문서를 먼저 읽고, 거기에 맞춰서 작업해줘.
```

버그 고칠 때:
```
<파일명>에서 <증상>이 나는데, 원인부터 찾아서 알려줘.
고치기 전에 뭘 어떻게 고칠 건지 먼저 설명해줘.
```

커밋·PR 만들 때:
```
지금 변경사항으로 커밋하려는데, 저장소 규칙에 맞는 커밋 메시지랑 명령어만 만들어줘.
실행은 하지 말고 나한테 명령어만 줘.
```

확인시킬 때:
```
방금 바꾼 거 빌드/테스트 돌려보고, 오류 있으면 고쳐줘.
```

### 꼭 붙이면 좋은 안전 문장

| 문장 | 언제 |
|---|---|
| **"실행하지 말고 명령어만 줘"** | push, PR, 파일 삭제처럼 되돌리기 어려운 작업 전 |
| **"고치기 전에 뭘 고칠 건지 먼저 설명해줘"** | 코드를 손대게 할 때 |
| **"<폴더>는 읽기만 하고 수정하지 마"** | 내 담당 밖 영역 보호 |
| **"진짜 그런지 확인해줘"** | AI가 단정적으로 말할 때 |
| **"뭘 바꿨는지 파일별로 정리해줘"** | 커밋 직전 |

### AI도 틀립니다

가장 흔한 실패는 **문서와 실제가 다를 때**입니다. 문서에 "라벨은 `fe`"라고 적혀 있어도 저장소엔
`frontend`만 있을 수 있습니다. AI가 문서만 보고 답하면 명령이 그냥 실패합니다.

그래서 **"진짜 그런지 확인해줘"** 한마디가 중요합니다. 좋은 도구는 실제로 조회해서 답을 고칩니다.

또 하나 — **AI가 "다 됐습니다"라고 해도 직접 확인하세요.** 화면을 열어보고, `git status`를 쳐보고,
실제로 돌려보는 건 사람 몫입니다.

### 피해야 할 것

- 한 번에 열 가지 지시 — 중간에 뭐가 틀어졌는지 못 찾습니다
- 결과 안 보고 다음 단계로
- 에러 메시지를 요약해서 전달 — **그대로 복붙**하세요. 요약하면 원인이 사라집니다

## 6. 자주 나는 문제

### push가 거부됨 (rejected)

내가 작업하는 동안 남이 먼저 올렸습니다.

```bash
git pull                  # 먼저 받고
# 충돌이 나면 아래 "충돌" 참고
git push
```

### 충돌(conflict)이 났다

같은 줄을 두 사람이 다르게 고쳤을 때입니다. 파일 안에 이런 표시가 생깁니다.

```
<<<<<<< HEAD
내 내용
=======
남의 내용
>>>>>>> develop
```

**혼자 판단하지 말고** 어느 쪽이 맞는지 확인한 뒤 고치세요. AI에게 이렇게 물으면 됩니다.

```
<파일명>에 충돌이 났어. 양쪽이 각각 뭘 하려던 건지 설명해주고,
어떻게 합치는 게 맞는지 알려줘.
```

### 한글이 `????` 나 `����` 로 깨짐

터미널로 파일에 한글을 쓸 때 인코딩을 안 정해준 경우입니다. **에러 없이 조용히 깨지니** 파일을
열어 눈으로 확인하세요.

```powershell
# Windows PowerShell
Add-Content 파일명 "내용" -Encoding utf8
```

### 큰 파일을 실수로 커밋

**한 번 커밋되면 지워도 기록에 영구히 남습니다.** 커밋 전에 확인하세요.

```bash
git status --short
git diff --cached --stat      # add 한 것들의 크기
```

이미 push까지 했다면 혼자 해결하려 하지 말고 팀에 알리세요.

### 비밀번호·API 키를 커밋

위와 같습니다. **즉시 팀에 알리고 해당 키를 폐기**하세요. 파일만 지우는 걸로는 해결되지 않습니다.

### 지금 어디에 있는지 모르겠다

```bash
git branch          # 현재 브랜치 (* 표시)
git status          # 상태
git log --oneline -5
```

## 7. 되돌리기

| 상황 | 명령 | 위험도 |
|---|---|---|
| 파일 하나 수정 취소 (커밋 전) | `git restore <파일>` | 낮음 |
| add 취소 (커밋 전) | `git restore --staged <파일>` | 낮음 |
| 방금 커밋 메시지만 고치기 | `git commit --amend -m "새 메시지"` | 낮음 (push 전에만) |
| 방금 커밋 취소, 변경은 유지 | `git reset --soft HEAD~1` | 중간 |
| 브랜치 통째로 버리기 | 새 브랜치 다시 만들기 | 낮음 |

**push한 뒤에 되돌리는 건 위험합니다.** 확신이 없으면 손대지 말고 물어보세요.

---

## 8. 절대 하지 말 것

- **`main` / `develop`에 직접 커밋·push** — 항상 작업 브랜치에서
- **`git push --force`** — 남의 작업을 지웁니다. 하라는 말을 듣기 전엔 쓰지 마세요
- **비밀번호·API 키·토큰을 코드에 넣기** — `.env` 같은 파일에 넣고 그 파일은 커밋 안 함
- **`node_modules` 같은 자동 생성 폴더 커밋**
- **내 담당 아닌 폴더 수정**
- **무슨 명령인지 모른 채 실행** — AI에게 "이 명령이 뭘 하는 건지 설명해줘"라고 먼저 물으세요

## 9. 막혔을 때 복붙할 문장

```
지금 <상황>인데 어떻게 해야 할지 모르겠어.
git status 결과는 아래야. 위험한 작업이면 먼저 경고해주고,
되돌릴 수 있는 방법부터 알려줘.

<git status 결과 붙여넣기>
```

```
아래 에러가 났어. 원인이 뭔지 설명해주고 해결 방법을 알려줘.
실행은 하지 말고 명령어만 줘.

<에러 메시지 그대로 붙여넣기>
```

```
지금 브랜치에서 뭘 했는지 정리해줘. 커밋해도 되는 상태인지도 봐줘.
```

## 10. 기억할 것 세 가지

1. **막히면 `git status`.** 대부분의 답이 여기 있습니다.
2. **되돌리기 어려운 작업 전엔 "실행하지 말고 명령어만 줘".** push, force, 삭제.
3. **AI가 "다 됐다"고 해도 직접 확인.** 화면을 열고, 돌려보고, 상태를 확인하는 건 사람 몫입니다.
